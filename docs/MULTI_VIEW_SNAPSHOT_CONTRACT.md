# Multi-view Snapshot Contract

Status: Implemented in this pass

Volundr creates deterministic geometry evidence after a worker has produced a
STL. Snapshot generation is observational: it does not change source,
topology findings, functional findings, candidate classification, or Current
working version promotion. A blocked candidate may still receive snapshots
when worker geometry exists; a pre-worker failure receives an explicit
`snapshot_not_applicable_before_worker` event and no fabricated packet.

## Packet

The durable packet schema is `geometry-snapshot-packet-v1`. It contains:

- project, workflow, revision, attempt, and candidate-state identifiers;
- the canonical millimetre coordinate frame (`Z` up, `Y` front, `X` right);
- registered BREP, STEP, and STL source artifacts and component IDs;
- deterministic renderer settings and version;
- whole-design, component, and optional section views;
- warnings and omission reasons;
- total, per-view, renderer, encoding, and registration timing;
- a stable `packet_hash` over geometry, camera, renderer, view, component,
  section, and warning content.

The packet artifact is immutable. Repeated observations use a new durable
snapshot batch directory and a new artifact row; they do not overwrite an
earlier packet or image. Packet lookup returns the newest registered packet,
while exports retain all snapshot batches.

## Views and camera policy

The standard ordered views are `isometric`, `opposite_isometric`, `front`,
`right`, and `top`. Component views use isometric, front, and top. Rear,
left, and bottom are available as optional view names but are not generated by
default. Cameras are orthographic, derived from the mesh bounds, and include
position direction, view direction, up vector, target, scale, and clipping
metadata. Identical geometry and settings produce identical camera metadata
and PNG bytes.

Rendering is a local deterministic STL rasterizer with a neutral background,
flat shading, and an optional edge overlay. It does not depend on a provider,
browser, source representation, or interactive viewer state.

## Sections

Sections are conservative evidence, not a general CAD sectioning engine. A
section is selected only when the execution context contains an internal-fit,
containment, cavity, wall-thickness, lid-engagement, or internal-clearance
signal. The packet records the plane origin, normal, kept side, reason, and
the section image. When no signal exists, it records an omission reason. A
failed section never blocks geometry promotion.

## Durable access

Registered artifacts remain under the project/revision durable store and are
served through ownership-checked APIs:

- `GET /api/revisions/{revision_id}/snapshots`
- `GET /api/revisions/{revision_id}/snapshots/images/{artifact_id}`
- `GET /api/revisions/{revision_id}/comparison`

The image endpoint returns PNG bytes only after verifying project, revision,
artifact type, and durable path ownership. API responses use an explicit
`*_not_available` status when a valid revision has no post-worker evidence;
this lets the frontend poll optional evidence without turning an expected
absence into a browser console error.

Snapshots are included in complete project packages. They are secondary
evidence and must not be confused with the authoritative STL, STEP, BREP,
source, or validation records.
